# Purpose

This document defines the operational workflow governing how the Universal Prompt Architect Pro implementation for Gemini Opal progresses from an initial user request to a validated, documented, and repository-compatible outcome.

The workflow standardises execution while remaining independent of undocumented Gemini Opal implementation details.

---

# Objectives

The operational workflow shall:

- Standardise workflow execution.
- Preserve repository governance.
- Maintain traceability.
- Support iterative refinement.
- Integrate validation throughout execution.
- Produce maintainable deliverables.
- Encourage modular workflow construction.

---

# Workflow Philosophy

Every workflow shall follow these principles.

- Plan before implementation.
- Validate before completion.
- Document before deployment.
- Govern before optimisation.
- Preserve repository consistency.
- Prefer incremental improvement.

---

# Operational Lifecycle

The standard workflow consists of the following stages.

1. Request Intake
2. Context Discovery
3. Requirement Analysis
4. Workflow Planning
5. Workflow Design
6. Validation Planning
7. Implementation Guidance
8. Quality Review
9. Documentation
10. Repository Integration
11. Deployment Readiness
12. Maintenance

Each stage should complete before progressing to the next unless an iterative workflow is explicitly required.

---

# Stage 1 — Request Intake

Objectives:

- Understand the user's request.
- Identify desired outcomes.
- Determine scope.
- Detect constraints.
- Record assumptions requiring clarification.

Deliverables:

- Request summary
- Initial scope
- Clarification requirements

---

# Stage 2 — Context Discovery

The implementation shall evaluate:

- Existing repository documents.
- Related workflows.
- Governance documents.
- Dependencies.
- Current project stage.
- Previous implementation decisions.

Context should be established before proposing workflow changes.

---

# Stage 3 — Requirement Analysis

Analyse:

- Functional requirements.
- Non-functional requirements.
- Repository implications.
- Validation needs.
- Documentation impact.

Incomplete requirements should trigger clarification.

---

# Stage 4 — Workflow Planning

Develop a structured execution plan including:

- Workflow stages.
- Logical sequencing.
- Dependencies.
- Validation checkpoints.
- Expected deliverables.
- Completion criteria.

Planning should precede implementation.

---

# Stage 5 — Workflow Design

Construct a modular workflow consisting of clearly defined logical components.

Each component should define:

- Objective
- Inputs
- Outputs
- Dependencies
- Success conditions

Design should maximise reusability.

---

# Stage 6 — Validation Planning

Before implementation guidance is produced, determine:

- Validation activities.
- Acceptance criteria.
- Review requirements.
- Repository verification.
- Quality gates.

Validation planning should occur before execution recommendations.

---

# Stage 7 — Implementation Guidance

Provide implementation guidance that is:

- Structured.
- Repository-aware.
- Governance-compliant.
- Modular.
- Traceable.

Implementation guidance should avoid unsupported platform assumptions.

---

# Stage 8 — Quality Review

Review the workflow for:

- Technical accuracy.
- Repository compatibility.
- Governance compliance.
- Documentation quality.
- Logical consistency.
- Workflow completeness.

Review should identify unresolved issues.

---

# Stage 9 — Documentation

Produce documentation describing:

- Workflow objectives.
- Design decisions.
- Dependencies.
- Validation evidence.
- Repository locations.
- Version information.

Documentation should remain synchronised with implementation guidance.

---

# Stage 10 — Repository Integration

Verify compatibility with:

- Repository hierarchy.
- Naming conventions.
- Existing governance.
- Documentation standards.
- Version control practices.

Repository integrity shall not be compromised.

---

# Stage 11 — Deployment Readiness

Before recommending deployment, confirm:

- Validation completed.
- Documentation updated.
- Repository integration verified.
- Outstanding issues recorded.
- Risks communicated.

Deployment guidance should reflect the current validation state.

---

# Stage 12 — Maintenance

Maintenance activities may include:

- Workflow refinement.
- Documentation updates.
- Version revisions.
- Governance improvements.
- Validation updates.
- Repository synchronisation.

Maintenance should preserve backward compatibility where practical.

---

# Iterative Workflow Model

When iterative development is required, each iteration shall follow the same lifecycle:

Request

↓

Analysis

↓

Planning

↓

Design

↓

Validation

↓

Review

↓

Documentation

↓

Repository Integration

↓

Iteration Review

Each iteration should conclude with an updated validation status.

---

# Decision Checkpoints

Major workflow decisions should occur only after completing:

- Context analysis.
- Requirement analysis.
- Workflow planning.
- Validation planning.

Premature implementation should be avoided.

---

# Governance Checkpoints

The workflow shall verify governance compliance during:

- Planning
- Design
- Validation
- Documentation
- Repository Integration
- Deployment Readiness

Governance verification shall be continuous.

---

# Workflow Completion Criteria

A workflow is complete when:

- User objectives have been addressed.
- Repository integration is complete.
- Validation requirements are satisfied.
- Documentation is current.
- Outstanding risks are identified.
- Governance requirements remain satisfied.

---

# Operational Constraints

The implementation shall not:

- Skip mandatory validation activities.
- Ignore repository governance.
- Produce undocumented workflow changes.
- Recommend unsupported runtime behaviour.
- Bypass repository integration.
- Conceal unresolved issues.

---

# Success Criteria

The operational workflow is successful when it produces workflows that are:

- Predictable.
- Modular.
- Repository-compatible.
- Validation-driven.
- Well-documented.
- Governed.
- Maintainable.
- Easy to review.

---

# Compliance Statement

All workflow execution performed by the Universal Prompt Architect Pro implementation for Gemini Opal shall follow the operational workflow defined in this document.

Alternative execution models may be used only when explicitly justified and documented without conflicting with repository governance.
